# Архитектура

Описываю словами, без кода: из чего состоит сервис и как через него ходят данные.

## Компоненты

| Пакет | За что отвечает |
|---|---|
| `domain` | Типы предметной области: аромат, позиция полки, позиция списка, запись журнала ношений |
| `features` | Книга признаков: считает вектор аромата из аккордов, нот, семейств, шлейфа и стойкости |
| `ridge` | Обучение личной модели: ridge-регрессия, аналитический leave-one-out, центрирование, защита от вырожденной матрицы |
| `predict` | Прогноз оценки, разложение на вклад признаков, пометка неуверенности, поправки по журналу ношений |
| `similar` | Похожесть: векторы аккордов, косинус, ближайшие соседи, совпадение по нотам |
| `importer` | Разбор выгрузки личного инструмента учёта: нормализация имён полей, отчёт о поправленном и пропущенном |
| `store` | Хранение: миграции, запросы (sqlc), сборка предметных объектов из строк базы |
| `golden` | Сверка с эталоном: чтение фикстур, сравнение с допуском, вывод расхождений |

## Путь данных

1. **Выгрузка.** Личный инструмент учёта отдаёт файл: полка, список, журнал ношений. Импорт читает его двумя наборами имён полей (живой экспорт и эталонный) и приводит к каноническим.
2. **База.** Записи попадают в PostgreSQL: ароматы, позиции полки и списка, записи журнала, история оценок и прогнозов. Схема живёт в миграциях.
3. **Признаки.** Для каждого аромата считается вектор: аккорды с шириной, ноты по ярусам, семейства, личные отметки. Личные отметки («как звучит на мне») перекрывают каталог только в признаках модели — витрина и похожесть остаются на данных каталога.
4. **Модель.** Личная ridge-модель обучается на оценках: сдвиг к коэффициентам «среднего пользователя» вместо сдвига к нулю, чтобы при пяти оценках прогноз не превращался в «средняя ± шум».
5. **Прогноз.** Оценка, её разложение на вклады и пометка неуверенности по рычагу. Пары «прогноз до оценки» пишутся по состоянию карточки до пробы, чтобы метрика измеряла то, чего модель знать не могла.

## Решения по надёжности

- **Идемпотентность на границе.** Один и тот же файл можно импортировать повторно: дубликаты по ключу не создают вторых записей, а поля доливаются только в пустые места.
- **Очередь без брокера.** Исходящие задачи и повторные попытки — на самом PostgreSQL (outbox), отдельного брокера в MVP нет: меньше движущихся частей.
- **Один пользователь — по одной операции.** Изменения одного пользователя сериализуются advisory-блокировкой, иначе две параллельные оценки могут обучить модель без одной из них.
- **Расширяющие миграции.** Новые ограничения и индексы добавляются так, чтобы старые данные и старый код продолжали работать: расширение, потом переключение, потом удаление старого.
